we are making a web based wysiwyg vue page designer. think of this like figma but for live vue components. The user can import a collection of components (their component library) and then they can be arranged, configured and styled within a canvas like view. the documents displayed in the canvas should be stored as code so that any code can be imported or can be generated externally. we will assume the user is using vite and they can apply custom vite config if required. also they can define the vue app instance used with a code file.

Proposed Architecture
Use a monorepo with three primary packages:
- packages/designer: Vue 3 editor UI
- packages/vite-plugin: Vite plugin providing project integration and controlled filesystem operations
- packages/shared: document AST, protocol types, component metadata, source transforms, and validation
- examples/basic: sample Vite application and component library
- tests/fixtures: representative Vue SFC inputs for round-trip testing
The existing Vite project remains the source of dependency resolution, aliases, plugins, app setup, and component implementations.
Canonical Document Model
Each document remains a normal Vue SFC:
<script setup lang="ts">
import { Button } from '@/components'
</script>

<template>
  <main class="page">
    <Button variant="primary">Continue</Button>
  </main>
</template>

<style scoped>
.page {
  display: flex;
  padding: 24px;
}
</style>
Internally, the designer derives an editable AST containing:
- Elements and registered Vue components
- Static attributes and editable prop bindings
- Text nodes
- Named and default slots
- Stable designer node IDs held in memory
- Source ranges for diagnostics and targeted updates
- Style rules and editable declarations
The SFC, not a JSON schema, remains authoritative. Unsupported Vue constructs are preserved as locked source regions whenever safe. The editor must not silently rewrite code it cannot represent.
Supported MVP Subset
Visually editable:
- Native HTML elements
- Registered Vue components
- Static attributes
- Literal bindings such as :count="3" and :enabled="true"
- Text content
- Default and named slots
- Child nesting and reordering
- Common CSS properties
- Scoped and unscoped SFC style blocks
- Classes already present in source
- Component props described by metadata or runtime analysis
Initially read-only or unsupported:
- v-for
- Complex v-if branches
- Dynamic components
- Arbitrary JavaScript expressions
- Nodes generated by render functions
- Template macros with unknown transforms
- Structural edits across unsupported constructs
- Programmatic styles whose values cannot be statically resolved
Unsupported constructs should still render in preview when Vite can compile them. The inspector displays why they cannot be visually edited.
Vite Integration
The user configures the plugin:
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import designer from '@vue-designer/vite'

export default defineConfig({
  plugins: [
    vue(),
    designer({
      documents: 'src/pages/**/*.vue',
      app: './src/designer-app.ts',
      components: './src/designer-components.ts',
    }),
  ],
})
designer-app.ts defines the preview app customization:
import type { DesignerAppSetup } from '@vue-designer/runtime'
import router from './router'
import './styles.css'

export default {
  setup(app) {
    app.use(router)
  },
} satisfies DesignerAppSetup
designer-components.ts explicitly exposes the component library and optional editor metadata:
import Button from './components/Button.vue'

export default {
  Button: {
    component: Button,
    props: {
      variant: {
        control: 'select',
        options: ['primary', 'secondary'],
      },
    },
  },
}
The explicit registry avoids unreliable filesystem inference and provides labels, categories, prop controls, defaults, events, slots, and example children.
Plugin Responsibilities
The Vite plugin should expose authenticated, narrowly scoped development endpoints for:
- Listing configured Vue documents
- Reading a document
- Parsing and validating proposed source
- Writing a document atomically
- Returning component registry metadata
- Serving the designer editor
- Building preview entry modules
- Reporting Vite/compiler diagnostics
- Watching externally changed files
Filesystem operations must:
- Resolve real paths and enforce configured roots
- Reject traversal and symlink escapes
- Require revision hashes on writes
- Write through a temporary file plus atomic replacement
- Refuse overwriting externally modified source
- Keep optional timestamped recovery copies during early development
Preview Isolation
Potentially untrusted code must not execute in the editor window.
Use:
- A sandboxed iframe without allow-same-origin
- A separate preview origin/port
- sandbox="allow-scripts" only
- A restrictive CSP
- postMessage with schema validation and per-session capabilities
- No direct preview access to filesystem endpoints
- Random short-lived authorization tokens for editor/plugin communication
- Strict origin and session validation
- No cookies or durable credentials in the preview origin
- Event and selection instrumentation injected by a Vite transform
The iframe protocol should support:
- Load compiled document
- Apply transient source updates
- Report render/compiler errors
- Report node rectangles
- Select and hover nodes
- Forward console diagnostics
- Request viewport settings
- Notify the editor after hot updates
Important limitation: executing genuinely malicious code on a developer machine through a local web server cannot be made perfectly safe with an iframe alone. The MVP can strongly isolate the editor and filesystem API, but high-assurance execution eventually requires a disposable container or remote preview environment.
Editor Layout
Desktop-first Chromium interface:
- Left: document tree and component palette
- Center: responsive iframe canvas
- Right: props, attributes, slots, and CSS inspector
- Top: document picker, viewport controls, undo/redo, source toggle, save status
- Bottom or overlay: compiler/runtime diagnostics
Canvas interactions use normal DOM flow:
- Drag components into valid parent/slot targets
- Reorder siblings
- Move nodes between compatible containers
- Select rendered nodes
- Inspect box-model overlays
- Resize only through semantic CSS controls such as width, flex, and grid properties
- No absolute-positioned Figma-style artboard model in the MVP
Source Transformation
Use Vue compiler tooling rather than regex:
- @vue/compiler-sfc for SFC blocks
- @vue/compiler-dom or @vue/compiler-core for template AST
- Babel parser for script analysis where needed
- PostCSS for style rules and declarations
- MagicString or range-based edits for minimal source changes
- Prettier as an explicit formatting action, not after every edit
The mutation pipeline:
1. Parse the current source and assign ephemeral node identities.
2. Convert a designer action into a typed source operation.
3. Apply the smallest possible source-range edit.
4. Reparse the entire SFC.
5. Reject the operation if parsing or structural validation fails.
6. Send the candidate source to preview.
7. Commit to disk only after explicit save or configured autosave.
8. Reconcile selection against the newly parsed tree.
Undo/redo should store source-level transactions, giving one consistent history across visual and code edits.
Implementation Plan
1. Workspace foundation
- Create pnpm workspace and TypeScript project references.
- Add Vue 3, Vite, Vitest, Playwright, ESLint, and formatting configuration.
- Establish shared protocol and AST types.
- Add a representative sample application.
2. Vite plugin
- Implement plugin configuration and validation.
- Add document discovery and safe read/write APIs.
- Add app and component-registry virtual modules.
- Serve editor and isolated preview entries on separate origins.
- Add file watching and revision-conflict reporting.
3. SFC document engine
- Parse template, script, and styles.
- Classify editable and unsupported nodes.
- Implement minimal operations: insert, remove, move, text update, attribute update.
- Implement CSS declaration updates.
- Add deterministic diagnostics and source locations.
- Verify parse-edit-parse behavior with fixture tests.
4. Preview runtime
- Render documents using the user’s Vite pipeline and app setup.
- Inject node instrumentation without changing saved source.
- Implement selection, hover, geometry, errors, and HMR messaging.
- Enforce iframe sandbox, CSP, and capability-based protocol.
5. Editor shell
- Build the three-pane layout and canvas viewport.
- Add document navigation and source editor.
- Add selection synchronization between tree, source, and preview.
- Add save state, external-change conflicts, and diagnostics.
6. Component authoring
- Load the explicit component registry.
- Build searchable palette and drag/drop insertion.
- Generate prop controls from supplied metadata, with Vue prop inference as fallback.
- Add slot-aware drop targets and child templates.
7. Styling
- Parse applicable SFC style rules.
- Add common layout, spacing, typography, color, border, flex, and grid controls.
- Show inherited/computed styles separately from editable declarations.
- Let users choose an existing rule or create a local class.
8. History and reliability
- Add source-transaction undo/redo.
- Add atomic writes and revision checks.
- Preserve selection through reparses.
- Add recovery for preview crashes and invalid edits.
9. Verification
- Unit-test parser classification and every source operation.
- Add round-trip fixtures containing supported and unsupported Vue syntax.
- Integration-test plugin path security and concurrent file changes.
- Playwright-test dragging, props, styles, saving, reload, and external edits.
- Add explicit adversarial tests for iframe/API isolation.
MVP Acceptance Criteria
- A user can add the plugin to an existing Vite Vue project.
- The designer lists configured .vue documents from that project.
- Documents render using the project’s aliases, plugins, styles, and app setup.
- Registered components can be inserted, nested, reordered, configured, and removed.
- Common CSS can be edited without absolute positioning.
- Visual edits produce readable, valid Vue SFC source.
- External source edits appear in the designer without data loss.
- Unsupported syntax is preserved and clearly identified.
- Undo/redo works across visual and source operations.
- Preview failures do not crash or gain privileges in the editor.
- Saves cannot escape configured project roots or overwrite unnoticed external changes.
